# Photo-layer locking and deselection — 0.2.30, 24 October 2026

The owner authorized per-photo lock/unlock controls, saved lock state and deselecting photos by tapping blank space in the Add/Edit widget page, then authorized committing, pushing main and pushing the new v0.2.30 tag for version 0.2.30 (32). This release also includes the previously committed header Refresh and animated layer-reordering updates. The owner will monitor the IPA build.

## Behaviour

- Every layer row now has an open/closed padlock button with a 48×48-point target. Its icon uses the readable app accent; its accessible name gives the action, layer name and current lock state. Locked rows also show “Locked” in their detail text. The existing responsive action row keeps eight-point spacing and wraps/stacks when needed, rather than shrinking the switch, padlock or menu.
- A locked photo remains visible/selectable. It keeps its outline while selected, with resize handles hidden. Dragging, pinching and corner resizing cannot alter it, and touching a locked top photo does not silently move a photo underneath it. Unlocking restores normal interaction.
- Lock also protects placement through Reset, Rotate, Flip and the position/size/crop controls. Those tools disable or disappear while locked, with guards on the underlying operations. Visibility, rename, opacity, blend mode, layer stacking and explicit confirmed deletion remain available. Lock protects a layer's own placement; changing the overall widget family still changes the canvas proportions for every layer as before.
- Lock/unlock is also available in the layer menu. Changes belong to the draft and persist through **Save widget**, like other edits. Cancelling keeps the original saved design. Locking an unselected row does not select it or close an unrelated layer's adjustment panel.
- Tapping empty canvas/workspace or blank page space clears the selected photo, its outline/handles, the outside ghost and the active adjustment panel. It does not hide, delete, move or save the photo. Tapping the photo or its layer row selects it again. The layer menu also offers **Deselect photo** as an accessible alternative.
- Existing off-canvas editing remains available: tapping an actual photo portion outside the widget boundary still selects that photo; tapping empty surrounding workspace deselects it. Taps during manipulation, layer reordering, a busy operation, backgrounding or departure cannot clear the active selection.

## Review, persistence and lifecycle

`WidgetLayer.Locked` is an optional Boolean with default `false`. The existing strict, source-generated JSON context saves it with the other photo edits; no schema version or database migration is needed. Old layers missing the field open unlocked and retain all prior geometry/blending. Invalid lock types fail decoding rather than being silently coerced. As with the previous optional editor fields, older app versions using strict decoding cannot read newly saved libraries with this field; downgrading such a library is unsupported.

Repository regressions verify save/reopen, failed-save preservation, unlock persistence, photo-byte preservation, slot assignment and App Group publication. The native widget reads design summaries and the saved composite; it does not interpret layer editor locks. The Swift compatibility regression now includes a locked layer. Rendering geometry ignores lock state, and the compositor's raster cache excludes it, so toggling a lock does not decode/re-rasterize the photo. Native image pixels remain a device/Xcode check.

Canvas and shared placement helpers both reject locked manipulation. A lock update during an existing gesture ends it without a late gesture write reverting the new lock. Disabled lock/menu/visibility controls recover after layer reordering. Review also corrected shared `ClipboardIconButton` press/click handling: disabling restores its press scale, and disabled clicks/presses are ignored. This applies to the new padlock and existing users of the same component.

The page's lightweight native tap recognizer does not cancel ordinary touches. It rejects native buttons/switches/sliders/text fields/editors and protected canvas, tool, adjustment-panel, layer-list and colour-picker areas. The canvas retains its own photo/empty-space hit testing; scrolling and drag recognition remain owned by their existing handlers. Page foreground/busy/gesture checks are repeated when a blank tap finishes. The native recognizer and its callback are removed when its handler disconnects. No timer, image asset, network request or storage write is introduced for deselection. Selection descriptions update even before the first layout pass, so VoiceOver does not depend on measured image bounds.
