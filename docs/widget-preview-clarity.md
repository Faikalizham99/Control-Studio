# My Widgets preview clarity

The owner reported that the size-filtered My Widgets cards look soft while Edit looks clear, then authorized the fix and subsequently authorized committing, pushing main and pushing a new version tag. This ships in **0.2.21 (23)** with the Counter appearance, Studio icon accent and iPhone widget-size updates. The owner will monitor the tag-triggered IPA build; native/device verification remains pending.

The code-level cause was the mismatch between display size and image source. `WidgetStudioService.Render` saves a full composite and a separate thumbnail capped at 256 pixels on its longest edge. `WidgetsPage` selected `ThumbnailPath` for its full-size family-proportioned cards. On a dense phone display this enlarges a small bitmap substantially. The editor instead draws the individual saved photo sources, so it retains more detail. For example, an XL thumbnail is approximately 156×256 pixels, while the representative XL canvas is 364×594 layout units before accounting for display density.

My Widgets now selects `RenderPath`, using the already saved full composite. The existing renderer bounds that composite to 1024 pixels on its longest edge and at most 2× representative size. Its intrinsic detail remains limited by those existing bounds and imported photo quality. No render regeneration, source-photo changes, catalog/schema migration or widget recreation is required. Tiny slot cards continue using thumbnails; the editor and native Home Screen image path are unchanged. Missing full renders show guidance to open Edit and save again rather than silently enlarging a thumbnail.

The current scroll/card layout and aspect-fit geometry are retained. Preview controls hold no image source until their frame is in or within 64 layout units of the visible scroll area. Bounds are calculated in the scroll content's coordinates, including the header and nested card padding. A selection policy prioritizes on-screen cards and caps live sources at six, including partially completed layouts. Sources leaving that selection are cleared before new sources are assigned. Repeated scroll events with the same selection do not restart loads. Filtering/rebuilding disposes old previews; leaving the page clears and permanently retires the old controls. The existing appearance reload builds fresh previews, so deleted/replaced render paths are not resurrected after returning from Edit. The source cap is not a measurement or guarantee of total UIKit/MAUI process memory.

Decorative images remain outside the accessibility tree and input-transparent. Existing native edit targets, card actions, Light/Dark background/contrast, retired-layout recovery, per-size shape and refresh/error states are retained. Preview loading performs no storage writes, sharing changes or new network requests. The existing page cancellation/epoch guards still prevent stale library reads from repainting another appearance.

The 0.2.21 release validation reran **295 automated tests**: 65 Core, 56 infrastructure, 145 app and 29 packaging/policy. Four new app tests cover lazy source loading, unchanged-selection reuse, release/disposal, missing-render guidance and contrast, 50-design scrolling, invalid/unmeasured bounds, prioritization and source caps during intermediate layouts. Managed iOS C# compilation, source/project checks, workflow lint and whitespace checks pass. Core/infrastructure tests run with reflection-based JSON serialization disabled. Native compilation and device checks remain pending.

An iPhone is still needed to verify actual clarity and first-load timing for all four sizes, fast scrolling through 50 designs, UIKit bitmap release/memory, smoothness, rotation and large text, light/dark appearance, VoiceOver and edit/delete targets, filter changes, missing renders and returning from a saved/canceled edit. Native Home Screen image quality is outside this page-only correction. No device visual or memory measurement has been performed on Windows.
